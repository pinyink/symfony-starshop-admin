# Integrate Module

Integrate an existing module generated by a CRUD Generator into the current Symfony project.

The generated module already provides a baseline implementation. Your responsibility is to inspect it, understand its existing functionality, identify integration gaps, and make the smallest changes necessary for it to work correctly within the target application.

Do not regenerate or rebuild the entire module unless the existing implementation is fundamentally incompatible with the project or the user explicitly requests it.

## Core Principles

- Inspect the generated module and the target project before changing code.
- Treat the generated code as an existing implementation, not a blank template.
- Treat the target project's source code and configuration as the source of truth for integration requirements.
- Preserve working generated functionality wherever possible.
- Follow the target project's architecture, conventions, dependencies, and security model.
- Make focused changes rather than broad refactoring.
- Distinguish integration defects from optional improvements.
- Verify actual behavior through relevant tests and checks.
- Preserve unrelated user changes.
- Do not claim successful integration without evidence.

## 1. Understand the Integration Request

Read `AGENTS.md` and relevant documentation under `docs/`, if present.

Determine:

- Which module is being integrated
- Where the generated module is located
- Which functionality must be available in the target application
- Whether the module has already been copied or partially integrated
- Whether it introduces new entities, routes, services, forms, templates, or assets
- Which existing application components it depends on
- Whether there are special business rules or acceptance criteria

If the module location is unclear, inspect the repository structure and relevant untracked or changed files before asking for clarification.

Do not assume that the module is complete, correctly generated, or compatible with the current application.

## 2. Analyze the Target Symfony Project

Use `project-analyzer` to inspect the existing application.

Determine the actual:

- PHP and Symfony versions
- Composer dependencies and autoloading configuration
- Directory structure and namespaces
- Routing conventions
- Controller and service patterns
- Doctrine entities, repositories, and relationships
- Form types and validation conventions
- Authentication and authorization strategy
- Twig layouts, templates, and reusable components
- Navigation and menu configuration
- Database migration strategy
- Testing framework, fixtures, and test database setup

Inspect existing modules that provide comparable functionality.

Do not impose a different architecture when the current application already has a suitable convention.

## 3. Analyze the Generated Module

Inspect the generated module before modifying it.

Identify its:

- Files and directory structure
- Namespaces and class names
- Routes and HTTP methods
- Controllers and business logic
- Entities and Doctrine mappings
- Repositories and query patterns
- Form types and validation
- Twig templates and assets
- Service dependencies
- Authorization assumptions
- Database schema and migration files
- Tests and testing requirements
- External packages or framework assumptions

Determine what is already implemented and what is missing.

Check for incomplete methods, placeholder code, generated defaults, hardcoded assumptions, invalid references, and dependencies that do not exist in the target project.

Do not treat every difference from the target project's conventions as a defect. Determine whether the difference actually prevents integration, violates a requirement, or introduces a meaningful risk.

## 4. Create an Integration Gap Analysis

Before modifying code, compare the generated module with the target application.

Classify each finding as one of the following:

- **Compatible:** Already works with the target application.
- **Required integration change:** Must change for the module to function correctly.
- **Security issue:** Requires remediation before the affected functionality is exposed.
- **Functional defect:** Existing behavior is incorrect or incomplete.
- **Optional improvement:** Useful but not required for integration.
- **Blocked:** Requires a decision, dependency, or external condition that is not yet available.

Identify:

- Files that can be reused unchanged
- Files requiring modification
- Missing files or configuration
- Required dependencies
- Required database changes
- Authorization and validation gaps
- Potential regressions to existing functionality
- Tests needed to verify integration

Keep the analysis focused on the requested module and its direct dependencies.

For complex or potentially destructive integration work, present the plan for approval before proceeding.

## 5. Resolve Namespace and Autoloading Compatibility

Inspect the generated namespaces and the target project's Composer autoload configuration.

Where necessary:

- Align namespaces with the target project's conventions.
- Correct class references and imports.
- Verify PSR-4 autoload mappings.
- Check service discovery and dependency injection.
- Confirm that referenced classes and interfaces exist.
- Detect duplicate class names or conflicting service definitions.

Do not modify Composer autoload mappings or install dependencies unnecessarily.

If new dependencies are genuinely required, explain why and obtain appropriate authorization before changing the dependency configuration.

## 6. Integrate Routing and Controllers

Verify that the generated routes are registered and compatible with the target application.

Check:

- Route paths and names
- HTTP methods
- Controller service registration
- Parameter conversion and entity resolution
- Request handling and response types
- Redirects and flash messages
- Missing-resource behavior
- Route conflicts with existing modules
- Authentication and authorization requirements

Follow the target application's routing conventions, whether routes are defined using attributes, YAML, PHP configuration, or another established approach.

Do not duplicate route definitions or change existing route names without a clear integration reason.

Ensure that every state-changing operation uses an appropriate HTTP method and authorization check.

## 7. Integrate Entities, Repositories, and Database Changes

Inspect the generated entity mappings and compare them with the target project's Doctrine configuration and existing data model.

Verify:

- Entity namespaces and mapping configuration
- Field types, nullability, defaults, and constraints
- Relationship ownership and inverse mappings
- Repository classes and service usage
- Unique constraints and indexes
- Referential integrity and deletion behavior
- Compatibility with existing entities and tables
- Migration consistency

If schema changes are needed:

1. Review the existing migration strategy.
2. Generate or create the required migration using the installed tooling.
3. Inspect the migration before execution.
4. Confirm that it does not unexpectedly drop, overwrite, or corrupt existing data.
5. Verify that it matches the intended entity changes.

Do not assume that generated migration files are correct.

Do not execute migrations against production or an unverified database.

If migration execution could cause data loss, downtime, or irreversible changes, stop before execution and obtain explicit authorization.

## 8. Integrate Forms and Validation

Check whether generated forms follow the target application's conventions.

Verify:

- Form types and entity binding
- Required fields and validation constraints
- Input types and transformation
- Handling of invalid submissions
- CSRF protection where appropriate
- Unique-value validation
- Relationship selection and entity ownership
- Protection of privileged or server-managed fields
- Consistency between form validation and business rules

Reuse existing validation conventions and services where appropriate.

Do not remove useful validation merely to make generated forms easier to integrate.

All security-sensitive rules must also be enforced server-side.

## 9. Integrate Authentication and Authorization

Inspect the target application's security configuration and authorization model.

Determine how the generated module should integrate with existing:

- Authentication requirements
- Role and permission definitions
- `access_control` rules
- `IsGranted` attributes
- Voters
- Resource ownership checks
- Navigation visibility rules

Requirements:

- Enforce access control on the server.
- Protect all relevant routes and sensitive operations.
- Verify resource ownership or tenant boundaries where applicable.
- Do not rely on hidden UI elements as authorization.
- Do not invent role names or permission conventions.
- Do not introduce a second authorization system without a justified requirement.
- Prevent unauthorized modification of protected fields.
- Ensure direct HTTP requests cannot bypass the intended permissions.

If the target application uses an RBAC bundle, inspect its actual configuration and implementation before integrating permissions.

Use `security-auditor` for focused analysis if the module introduces significant security-sensitive behavior.

Do not expose the module until critical authorization gaps have been addressed.

## 10. Integrate Twig Templates and Frontend Assets

Inspect the target application's existing layout, design system, and asset pipeline.

Where applicable:

- Extend the correct base layout.
- Reuse existing navigation, breadcrumbs, and components.
- Align template paths and naming conventions.
- Verify that referenced templates and assets exist.
- Preserve the project's existing frontend framework.
- Ensure forms display validation errors correctly.
- Ensure listing and detail pages handle empty states.
- Check links, route references, redirects, and action buttons.
- Verify Twig escaping and avoid unsafe HTML rendering.
- Add navigation entries only when the module should be accessible through the application's navigation system.

Do not introduce a new CSS framework or frontend build system just to accommodate the generated module.

Avoid redesigning unrelated pages.

## 11. Review File Uploads and External Dependencies

If the generated module handles file uploads or external services, inspect those flows carefully.

For file uploads, verify:

- Server-side validation
- File size and allowed content types
- Safe filename generation
- Storage destination and access policy
- Path traversal prevention
- Handling of failed uploads
- Cleanup and overwrite behavior
- Authorization for protected downloads

For external dependencies and integrations, verify:

- The required package or service exists
- Configuration is available in the target environment
- Credentials are not hardcoded
- Failures are handled appropriately
- Network access and side effects are controlled

Do not install packages or access external systems without a justified need and appropriate authorization.

## 12. Implement Focused Integration Changes

After the gap analysis, implement the smallest set of changes necessary to achieve the requested integration.

Prioritize:

1. Missing or broken references
2. Namespace and autoloading issues
3. Route registration and controller compatibility
4. Entity mapping and database compatibility
5. Required validation and business rules
6. Authentication and authorization
7. Template and asset integration
8. Error handling and user feedback
9. Automated tests
10. Documentation

Preserve working generated code.

Avoid:

- Regenerating the whole module without justification
- Rewriting working controllers or templates solely for style
- Duplicating existing services or utilities
- Introducing unnecessary abstractions
- Refactoring unrelated modules
- Silently changing the module's intended behavior

If a generated component is fundamentally incompatible, explain the incompatibility and replace only the affected component when possible.

## 13. Implement Integration Tests

Use `test-engineer` to design and implement tests for the integrated module.

Cover relevant behavior, including:

- Route availability and expected HTTP responses
- Successful CRUD operations
- Validation errors and invalid requests
- Authentication and authorization
- Resource ownership and inaccessible records
- Doctrine persistence and entity relationships
- Template rendering and redirects
- File uploads and failure handling, if applicable
- Regression scenarios involving existing modules

Reuse the target project's existing test framework, fixtures, and conventions.

Confirm that the test database is isolated before running tests that reset data or modify the schema.

Do not use production data or credentials for tests.

Do not weaken tests to conceal integration defects.

## 14. Execute Verification

Inspect the target project's configuration to determine which checks are available.

Run relevant checks in a safe order, where applicable:

1. PHP syntax checks for changed PHP files
2. Composer autoload validation when appropriate
3. Symfony container and configuration checks
4. Route inspection
5. Twig and YAML validation
6. Doctrine mapping and schema validation
7. Focused tests for the integrated module
8. Related regression tests
9. Full test suite when practical

Potential commands include:

- `composer dump-autoload`
- `php bin/console lint:container`
- `php bin/console lint:twig templates/`
- `php bin/console lint:yaml config/`
- `php bin/console debug:router`
- `php bin/console doctrine:schema:validate`
- `php bin/phpunit`

Use only commands supported by the project's installed tooling and Symfony version.

Treat `composer dump-autoload` as a generated-file operation and inspect the working tree afterward.

Do not run database-changing commands merely to verify syntax or configuration.

Do not claim a check passed unless it was actually executed and its result inspected.

## 15. Review the Integrated Module

Use `project-analyzer` to check consistency with the target application's architecture where needed.

Use `security-auditor` to review significant security-sensitive integration changes.

Use `test-engineer` to evaluate test coverage and diagnose failures.

Review the final changes for:

- Functional completeness
- Compatibility with the target project
- Correct database mappings and relationships
- Validation and authorization
- Secure output rendering
- Error handling
- Regression risks
- Unnecessary code changes
- Missing tests and documentation

Use `/review` for a broader final review when appropriate.

If defects are discovered, address them within the authorized scope and rerun the relevant checks.

## 16. Update Documentation

Update relevant documentation when integration changes:

- Application architecture
- Module dependencies
- Entity relationships
- Routes or permissions
- Database migrations
- Configuration requirements
- Operational or deployment procedures
- Testing instructions

Preserve useful existing documentation and avoid redundant documentation.

Do not document credentials, tokens, or secret values.

## 17. Final Integration Report

Provide a concise report containing:

### Module Overview
- Module name and purpose
- Existing functionality reused
- Important integration decisions

### Gap Analysis
- Compatibility issues identified
- Required changes made
- Security or functional defects addressed
- Optional improvements left out of scope

### Files Changed
- Files created
- Files modified
- Purpose of important changes

### Database and Dependencies
- Entity or mapping changes
- Migration files created
- Whether migrations were executed and in which verified environment
- Dependency changes and rationale

### Security
- Authentication and authorization integration
- Important security issues addressed
- Remaining security limitations

### Verification
- Commands actually executed
- Test results
- Failed or skipped checks
- Environment limitations

### Remaining Work
- Unresolved blockers
- Required manual steps
- Recommended follow-up actions

## Scope and Safety

- Integrate the existing generated module; do not rebuild it without justification.
- Follow the target project's actual architecture and conventions.
- Do not modify unrelated modules without a clear reason.
- Do not install, remove, or update dependencies without appropriate authorization.
- Do not run destructive migrations or database operations against unverified environments.
- Do not access production systems or modify production data without explicit authorization.
- Do not expose secrets or sensitive data.
- Do not weaken security controls or validation.
- Preserve unrelated user changes.
- Do not commit, merge, push, or rewrite Git history.
- Do not claim successful integration without executed verification.
- If safe integration is blocked, report the blocker instead of making speculative changes.

## Completion Criteria

Integration is complete when:

- The generated module and target project have been analyzed.
- Compatibility gaps have been identified and classified.
- Required integration changes have been implemented.
- Existing generated functionality has been preserved where possible.
- Routes, services, entities, templates, and dependencies work with the target project.
- Required authorization and validation are enforced.
- Database changes are represented by reviewed migrations where needed.
- Relevant automated tests and verification checks have been executed when possible.
- Existing functionality has been checked for regressions.
- Documentation and remaining work are reported accurately.
